## Declarative registration assessment

The helper derives bounded JSON Schema from form metadata while executable handlers come only from an explicit own-property function map. Dangerous/duplicate names, unsupported secret/action controls, invalid bounds, missing descriptions and preexisting tool names reject. Definitions are collected before registration. Registration failure cleans up owned registrations. Cleanup compares exact current registered definition identity, preserving an external replacement. Prefix handling delegates to the kit's prefixed lookup/invocation contract.

The generated schema performs runtime validation through the normal kit path, including required fields, numeric types/min/max, string lengths and additional-property denial. HTML is not treated as execution code or authorization. Ordinary disabled controls, select options, HTML validity and arbitrary business rules are not a general authorization policy, and current documentation says so. Schema constraints and explicit human/application policy remain the actual boundary.

The strengthened current test covers a valid registered prefixed call, invalid typed/additional inputs, dangerous and duplicate fields, inherited handler denial, all-forms preflight, idempotent cleanup, and preservation of external replacement. It could further separate preflight and replacement into individual test names and use validation-specific patterns for its two runtime rejection assertions; that is a test clarity improvement, not an observed runtime defect.

## Discovery and release assessment

Express catalogs default private, require literal true from authorization callbacks, retain authorization even in explicit public mode, set private/no-store, and authorize HEAD without serializing a catalog body. Local manifest paths, printable bounded header values, capability allowlists and security-option types are validated. Discovery advertises metadata; it does not supply execution authorization or a stdio transport. Documentation keeps that distinction.

CI uses immutable action references, immutable npm install, Node 22/24 release gates, a separate isolated Python wheel-import job and an aggregate build gate that requires both jobs to succeed. The release command includes formatting, types, SDK/Studio tests/builds, packed consumers, native/browser/CSP/accessibility checks, Python tests and dependency audit. The browser script was absent during initial recovery reading and present on recheck; that recovery interval is not a final missing-file finding.

Current release documents distinguish historical lost-worktree test evidence from fresh recovery checks and leave complete current release/CI verification pending. They do not relabel deterministic signatures/receipts as funded validation and describe application signing/verifier, RPC/finality, non-atomic resource delivery, memory-only history and experimental-browser limits. No publication/deployment/funded action is implied by merge authorization.
